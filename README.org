#+TITLE: run.py
#+VERSION: v026
#+STARTUP: overview

* Purpose

=run.py= is a small manifest-driven executor for reproducible analytical
packages.

The runner is designed around three manifest operations:

- =load_csv=
- =run_sql=
- =export_sql=

This version implements the first dry-run manifest validation pass. Execution
behavior will be implemented in later commits.

* Command-line contract

Dry run:

#+begin_src shell
python3 run.py --dry-run path/to/manifest.csv
#+end_src

Dry run with verbose diagnostics:

#+begin_src shell
python3 run.py --dry-run --verbose path/to/manifest.csv
#+end_src

Execution:

#+begin_src shell
python3 run.py --run path/to/manifest.csv
#+end_src

The =--dry-run= and =--run= options are mutually exclusive.

* Manifest schema

The manifest has exactly five columns, in this order:

#+begin_example
step,mode,input,output,authority_zone
#+end_example

The final column is intentionally =authority_zone=. A later validation
commit will enforce this exact header structure.

* Manifest modes

Allowed modes are:

- =load_csv=
- =run_sql=
- =export_sql=

* Authority zones

Each manifest row must eventually declare exactly one authority zone from:

- =source=
- =prepared=
- =review=
- =focused=
- =inform=
- =business=
- =report=

These names are defined centrally in =manifest_schema.py= so later
validation and execution code can consume one canonical contract.

* Dry-run validation

The dry run now validates:

- manifest file existence
- exact manifest header order
- positive integer step values
- duplicate step values
- allowed modes
- allowed authority zones
- required input values
- required outputs for =load_csv= and =export_sql=

Validation returns nonzero when any issue is found and prints a concise,
human-readable message plus a corrective hint.

Example:

#+begin_src shell
python3 run.py --dry-run tests/fixtures/valid_manifest.csv
#+end_src

* Human-readable dry-run reporting

Validation is now rendered as command-line prose rather than raw internal
validation records.

A successful dry run reads like:

#+begin_example
Dry run for package/manifest.csv
Result: ready to run.
#+end_example

A failure reads like:

#+begin_example
Dry run for package/manifest.csv
Result: not ready to run. Found 1 problem.

1. Step 3 failed because Mode 'bad_mode' is not allowed.
  What to do: Use one of: load_csv, run_sql, export_sql

No package steps were executed.
#+end_example

With =--verbose=, the report may also expose internal validation type names
and the canonical manifest contract. The normal mode stays focused on prose.

* Verbose dry-run reporting

A successful verbose dry run now describes the execution plan row by row.

For each manifest step it shows:

- manifest line number
- step number
- mode
- authority zone
- declared input
- declared output
- resolved input path when present
- resolved output path when present

Relative paths are resolved from the directory containing the manifest.
This keeps the package portable as a unit.

Verbose inspection happens only after structural validation succeeds.

#+begin_src shell
python3 run.py --dry-run --verbose path/to/package/manifest.csv
#+end_src

* Run execution skeleton

=--run= now follows the same validate-first discipline as =--dry-run=.

The flow is:

1. validate the manifest
2. stop immediately if validation fails
3. inspect the manifest in declared order
4. build an execution result for each step

Concrete handlers are intentionally not implemented yet. Each valid step
is reported as =pending= so the execution contract exists before any data
movement is introduced.

Example:

#+begin_src shell
python3 run.py --run path/to/package/manifest.csv
#+end_src

The current output makes it explicit that no package operations have been
executed yet.

* load_csv execution

The first concrete execution mode is now implemented.

A manifest row such as:

#+begin_example
1,load_csv,data/product.csv,source_product,source
#+end_example

means:

1. resolve =data/product.csv= relative to the manifest directory
2. create a fresh DuckDB database for the run
3. create or replace =source_product=
4. load the CSV with DuckDB =read_csv_auto=
5. report the loaded row count

The execution database is:

#+begin_example
artifacts/package.duckdb
#+end_example

relative to the manifest directory.

Every =--run= recreates that database, preserving the fresh-run discipline.

=run_sql= and =export_sql= remain pending.

* Dependency

#+begin_src shell
python3 -m pip install -r requirements.txt

* run_sql execution

The second concrete execution mode is now implemented.

A manifest row such as:

#+begin_example
2,run_sql,sql/prepared_product.sql,,prepared
#+end_example

means:

1. resolve the SQL file relative to the manifest directory
2. read the SQL file as UTF-8 text
3. reject an empty SQL file
4. execute the SQL against the same DuckDB connection used by prior steps
5. preserve objects created by earlier steps in the same run

This makes layered SQL possible. For example, step 1 can load
=source_product= and step 2 can create =prepared_product= from it.

The =output= column is intentionally unused for =run_sql= because the SQL
file itself owns the names of the relations it creates.

=export_sql= remains pending.

* export_sql execution

The third concrete execution mode is now implemented.

A manifest row such as:

#+begin_example
3,export_sql,prepared_product,artifacts/product.csv,report
#+end_example

means:

1. treat =prepared_product= as the relation to export
2. resolve the output path relative to the manifest directory
3. create the output directory when needed
4. export the result as a CSV with a header
5. report the exported row count

The =input= field may also contain a =SELECT= or =WITH= query instead of a
relation name.

With this commit, all three manifest operations are executable:

- =load_csv=
- =run_sql=
- =export_sql=

The minimal end-to-end execution path is therefore complete:

#+begin_example
CSV source
  -> DuckDB source table
  -> SQL-created prepared view
  -> CSV export
#+end_example

* Execution failure handling

Runtime failures are now converted into structured execution issues and
rendered as prose.

The runner stops at the first failing step. Earlier completed steps remain
reported, while later steps are not executed.

A failure report includes:

- the failing step
- the manifest mode
- a plain-language reason
- a corrective hint
- the number of completed steps
- confirmation that later steps were skipped

Verbose mode additionally shows the internal execution problem type.

Common categories include:

- =input_missing=
- =permission_denied=
- =text_encoding_error=
- =duckdb_error=
- =invalid_execution_input=
- =execution_error=

This preserves the early-failure design during actual execution, not only
during dry run.

For each manifest step it can report:

- relations created
- relations referenced
- authority zone

Example shape:

#+begin_example
Step 11 [review] creates: review_bundle;
  references: prepared_bundle, prepared_product_bundle, prepared_product
#+end_example

This commit discovers dependencies but does not yet reject unresolved
dependencies. Validation of those dependencies belongs to the next commit.

The discovery logic is intentionally conservative and supports the SQL
patterns used by the package. It is not intended to be a complete SQL parser.

* Dependency validation

Dry run now validates discovered relation dependencies.

A referenced relation must already have been created by an earlier manifest
step.

For example, if a Review-layer SQL file contains:

#+begin_src sql
SELECT * FROM prepared_missing;
#+end_src

but no earlier step creates =prepared_missing=, dry run reports the package
as not ready to run.

The execution path uses the same dependency validation before opening the
DuckDB execution sequence, so unresolved dependencies are blocked before
any package steps execute.

This preserves the validate-first contract while extending it from manifest
shape to analytical relation flow.

* Authority-zone progression

Dry run now checks the direction of relation dependencies across authority
zones.

The permitted direction is:

#+begin_example
source
-> prepared
-> review
-> focused
-> inform
-> business
-> report
#+end_example

A step may depend on a relation created in the same zone or an earlier
zone.

A step may not depend on a relation created in a later zone.

For example, a =source= step depending on a relation produced in =business=
is rejected as:

#+begin_example
backward_authority_dependency
#+end_example

This check is dependency-based rather than simply requiring all manifest rows
to be grouped by zone. Independent branches can therefore remain flexible
while the authority direction of actual dependencies stays explicit.

* Relation contracts

Packages may now optionally declare expected relation structure in:

#+begin_example
specifications/relation_contract.csv
#+end_example

The strict schema is:

#+begin_example
relation,column,data_type,key
#+end_example

Each row declares one expected column. Composite keys are represented by
marking multiple columns of the same relation as =key=true=.

Dry run checks that:

- contracted relations are produced by the package
- grain keys appear in the contract when both are declared
- grain keys are marked =key=true=

Verbose dry run displays the declared contracts.

A runtime validator is also included for checking realized DuckDB columns,
data types, and key uniqueness.

* Package test command

The runner now has a package-level test lifecycle:

#+begin_example
python3 run.py --test MANIFEST
python3 run.py --test --verbose MANIFEST
#+end_example

A package test performs, in order:

1. manifest and package preflight validation
2. dependency validation
3. authority-zone validation
4. grain and relation-contract specification validation
5. artifact-specification validation
6. fresh package execution
7. runtime relation-contract checks against DuckDB
8. deterministic artifact comparison

The command stops before execution when preflight fails. After execution it
checks realized relation columns, types, key uniqueness, and declared golden
artifacts.

The final result is an explicit =PACKAGE TEST: PASS= or
=PACKAGE TEST: FAIL= and the process exit status matches that result.

This command brings together the analysis-contract features developed across
cycle 2 into one package-facing test operation.

* Dry run without DuckDB

require the DuckDB Python package to be installed.

#+begin_example

Execution remains a runtime boundary. =--run= and a package test that reaches
execution require DuckDB and report the installation command when it is
